Este proyecto no usará el plugin faro para gestionar los procesos.
Este proyecto se construirá usando Tauri como entorno de ejecución, tanstack start como framework para las vistas y tailwind como hoja de estilos.
La aplicación guardará datos tanto en una base de datos Sqlite, en local, como en archivos de tipo md.
La aplicación será de carácter multi idioma. De momento sólo usaremos inglés y castellano, en sus variantes genéricas sin regiones ("en" y "es"). Por defecto todo será en inglés. Tanto para el código fuente como para la base de datos pondremos todo en inglés (código, tablas, campos, etc). Para las traducciones habrá una carpeta "i18n" con un único archivo json, organizado por componentes. Por componente se entiende cualquier elemento visible en la web, por básico que sea, como un botón o un label. Cada componente tendrá una sección "languages" con el texto en cada idioma, siempre primero en inglés y luego en castellano. El i18n solo se usa para los textos de la interfaz: cualquier texto que no venga de la base de datos o de un fichero md. Si falta un texto en el idioma activo, se mostrará en inglés. Cada vez que te dé un componente con texto en un idioma, crearás siempre la traducción al otro. El idioma elegido se guardará en settings.json para mantenerlo entre sesiones.
Por defecto, tanto la base de datos como los archivos de la aplicación se guardarán en la misma ruta donde esté el ejecutable en las carpetas "bbdd" y "notes". En esta última irán los archivos md. Reservaremos el nombre de carpeta "docs" por si más adelante permitimos adjuntar documentos externos. Todos los documentos serán en formato md a menos que se especifique lo contrario. La configuración de la app se guardará en el archivo settings.json, junto al ejecutable, para poder configurarla a mano sin tener que buscar el ajuste exacto; otras cosas que se gestionan desde Ajustes, como la creación de proyectos, se guardarán en la base de datos. Cada elemento de los ajustes especificará dónde se guarda. Los ítems se podrán cerrar, pero no borrar.
Todos los estilos se generarán en una hoja de estilos global. Todo lo que son colores y fuentes se pasarán por variables a los archivos para los "themes".
Se creará una plantilla base para crear los themes. Contendrá todas las variables. Esta plantilla no se cargará nunca en una vista, será para crear los campos que debe incluir un tema, pero no tendrá valores.
Se crearán dos temas base: "Light" y "Dark". Tendrán todas las variables de la plantilla y se le asignarán valores.
El objetivo de la aplicación se servir como gestor de tareas, unificando proyectos, github y un "ToDo" personal. Además permitirá ejecutar sesiones de consola para lanzar asistentes de IA.
La aplicación será una vista que se dividirá en 2 columnas. Serán 2 divs que no tendrán espacios ni márgenes al rededor. El primero tendrá los menús, el segundo será el contenedor de la vista principal.
Aunque los elementos de los datos serán muy similares, para mantenimiento y futuros evolutivos, crearemos una tabla para cada tipo de ítem. Los ítems mantendrán una jerarquía. Para todos los items, aunque haya dado el nombre en castellano, cuando crees las tablas, pon todos los nombres en inglés, tanto para tablas como para campos.
El ítem principal será "Proyectos" y crearemos la tabla "projects" para gestionarlos. El id será autonumérico de tipo entero. Tendrá el campo "name" de texto con el nombre o título del ítem. Agregaremos un campo de texto que se llamará slug y que usaremos como id público. Este campo será único, para que no se repita. Si en algún momento se crea un proyecto con el mismo slug agregaremos un "_2" como sufijo. En el ejemplo he puesto un 2, pero será un contador de repeticiones. Tendrá también el campo status_id que será el FK de la tabla statuses. Tendremos los campos created_at, updated_at, closed_at y deadline que serán fechas de tipo entero.
El siguiente ítem, por jerarquía, será "Épicas". Crearemos la tabla epics para este item. Será un clon de la tabla projects. Agregaremos el campo "project_id" que será el id de la tabla projects al que está asociado. Una épica siempre irá asociada a un proyecto. Tendrá también el campo "repo_id" que indicará el repo al que pertenece, igual que en las macros.
El siguiente es "Macros" que tendrá la tabla macros y será un clon de projects. Agregaremos los campos "project_id" y "epic_id". Una macro puede depender de una épica y entonces el campo project_id será null. También puede depender directamente de un proyecto y el campo epic_id será null. Agregaremos los campos "branch" y "issue" que serán de texto para guardar las ramas e issues del repositorio. Tednrá también el campo "repo_id" que indicará el repo al que pertenecen la rama y el issue.
El último ítem será "Tareas" y tendrá la tabla tasks. Será un clon de la tabla projects. Las tareas son el desglose más pequeño del trabajo, por lo que tendrán sólo el campo "macro_id" y sólo pueden depender de una macro. Las tareas salen del archivo tasks.md que está en el repositorio, en la rama de la macro, en la ruta openspec/changes/<<nombre_de_la_rama>>/tasks.md, sustituyendo cada "/" del nombre de la rama por "_". Ese archivo lo genera Faro al crear la rama; aunque aquí no usamos Faro, nos aseguraremos de que exista: si no existe en la rama, se crea y se hace commit para guardarlo. Si se crea una tarea a mano, se actualiza en el archivo y se hace un commit por cada tarea. Si una macro no tiene rama, por ahora no se hará nada. La tabla tasks se mantiene sincronizada con el archivo. Si se elimina una tarea desde fuera de la app, la tarea se marcará como cancelada. Cada línea de tasks.md llevará el slug de la tarea en un comentario HTML (<!-- slug:... -->) para identificarla aunque se renombre; las líneas sin slug se tratarán como tareas nuevas y la app les añadirá el slug. Cuando se cambie a una macro o a cualquier elemento asociado a una rama, se usará git para cambiar la rama activa en la ruta del repositorio (repos.path).
Crearemos también la tabla "repos". Tendrá también un id numérico auto incremental. Tendrá un campo texto para guardar la url del repositorio. Tendrá también el campo "path" de texto con la ruta en disco duro donde está clonado el repositorio. Las rutas en disco local van siempre asociadas al repositorio, ya que un proyecto puede tener varios.
Crearemos una tabla para cruces, con id numérico autoincremental y los campos "project_id" y "repo_id". Esta tabla servirá para decidir los repositorios que pueden pertenecer al proyecto.
Crearemos también la tabla "statuses" que tendrá el estado de los ítems. Tendrá un id numérico autoincrementeal. Un campo de texto para el "nombre", otro para "descripcion" y un campo "prority" de tipo numérico. Los nombres y descripciones de los estados se guardarán en inglés y no se traducirán. De momento pondremos los estados:
  name	      description	                                                                                                                    priority

Pondremos también la tabla "labels" que tendrá un id numérico autoincremental. Un campo "name" de tipo texto y un campo "color" también de tipo texto. Añadiremos la tabla "items_labels" que tendrá un id como campo numérico auto incremental, un campo "label_id" que será el FK de la tabla labels, un campo "item_id" y el campo "item_type" que será de texto y admitirá los valores "project", "epic", "macro" o "task".
Respecto a la vista, pondremos un contenedor principal para ajustes visuales globales sin margenes y espacios. Estará dividido en dos columnas. Ambas estarán divididas por un fino borde que permitirá ser arrastrado con el ratón para cambiar el tamaño de las columnas. Solo se podrán arrastrar los separadores que se especifiquen expresamente; el resto, como el del menú de Ajustes, serán fijos. Al pasar el ratón por el borde, el cursor cambiará y el borde se resaltará; con doble clic volverá al ancho por defecto. El ancho actual, el ancho por defecto y los límites mínimo y máximo se guardarán en settings.json.
En la columna o div de la izquierda, pondremos un sidebar y se verá en la parte superior el logo de la aplicación. Justo debajo tendrá el menú "Home" que aún no tendrá funcionalidad y luego se listarán los proyectos. Cada proyecto será parte del propio menú.Todos los proyectos irán dentro de un div que, si el contenido se excede del alto del div, tendrá scroll vertical. Si el texto no cabe en horizontal, se cortará con "..." al final del texto. En la parte inferior de la vista aparecerá el menú "Ajustes".
Cuando pulse en un proyecto del menú, en la vista de la derecha se mostrará un componente que se llamará main_view. Este componente tendrá dos columnas. Ambas estarán divididas por un fino borde que permitirá ser arrastrado con el ratón para cambiar el tamaño de las columnas. En la izquierda cargará el componente "ToDo" y en la derecha se cargará el componente que llamaremos "minion".
El componente ToDo será el listado de epics, macros y tasks asociadas al proyecto. Cada elemento tendrá anidado los items inferiores en jerarquía que estén asociados a los items mostrados. Cada item tendrá un espacio tabulado desde la izquierda independientemente de que esté asociado a un elemento suprior o no. Los items que tengan otros ítems anidados, podrán plegarse o expandirse.
Todos los elementos de la vista se podrán editar haciendo doble click en el elemento, lo que abrirá un popup que permitirá su edición. Permitirá editar el título o nombre, el estado con un desplegable de la tabla statuses o asociar uno de los repositorios del listado de repositorios asociados al proyecto. Si se trata de una macro, permitirá escoger rama e issue que haya en ese proyecto. El listado de ramas e issues se refrescará directamente desde la API al desplegar el select para escoger.
Cuando marque una épica, macro o tarea con un estado concreto, ese estado evolucionará hacia arriba usando el que tenga priority más alto. Es decir, si establezco una task en el estado con prortity 99, todos los elementos superiores cambiarán a ese estado si su estado tiene una priority menor. Además, si un elemento cambia de estado, todos los ítems inferiores tendrán el mismo estado que el asignado. Antes se mostrará un mensaje informando de esta situación y pidiendo confirmación. Si todos los elementos del mismo nivel tienen el mismo estado, el elemento superior adquiere ese mismo estado. Un elemento nuevo puede reabrir el superior. El campo closed_at se rellenará al pasar a Done o Canceled y se vaciará al reabrir. Los cambios hechos en tasks.md se propagan igual que los de la app, y cambiar una tarea a Done desde la app se refleja en el documento. Cada cambio de estado hará un único commit con todas las tareas afectadas.
El componente "minion" tendrá dos divs horizontales (uno encima del otro), separados por una barra que permita arrastrar para establecer la altura. En el de arriba tendrá pestañas. La primera, siempre existirá y se llamará "Notes". Al entrar por primera vez, buscará en el directorio asignado en opciones (el mismo de la aplicación por defecto) un fichero con el nombre "<<tipo_item>>_<<id>>" siendo tipo project, epic, macro o task y el id el auto numérico de la base de datos. Si no existe, lo crea. El fichero tendrá extensión md. Si se renombra un ítem, se mantendrá su fichero asociado. Si se cambia la carpeta de notas y la antigua tiene datos, un mensaje ofrecerá importar todas las notas, solo las de los ítems no cerrados o no importar nada. Las notas importadas se moverán, y si ya existe un fichero con el mismo nombre se preguntará qué hacer.
Al pulsar un proyecto, el campo notes tendrá el fichero project_<<id>>.
El div inferior será un emulador de consola de terminal. La terminal sólo se abrirá desde épicas y macros, nunca desde proyectos ni tareas. Se abrirá en la ruta local del repositorio asociado, que sale del campo "path" de la tabla repos. Si no hay ningún repositorio con path, no se abrirá la terminal; si el repositorio asociado no tiene path, la terminal se deshabilitará. Las ramas saldrán del repositorio asociado y no se escribirán a mano, por lo que una rama siempre tendrá repositorio.
La vista completa no se destruirá de memoria para no cerrar la terminal. Quedará en memoria cada vez que se entre en un proyecto.
La vista "Settings" se dividirá en dos columnas. La de la izquierda será un listado tipo UL de html, como un menú vertical. Más adelante aplicaremos los diseños. Cuando se pulse en un setting, se mostrará en la columna de la derecha.
El primer setting que añadiremos será "Projects" y mostrará en la columna de la derecha un formulario que permitirá crear un proyecto. En el formulario se podrán agregar repositorios. Cuando se agregue un repositorio, se añadirá a la lista de repositorios (en su tabla de la base de datos). El slug se generará automáticamente, pero será editable. El estado estará en un select con todos los estados de la tabla statuses, con "Triage" seleccionado por defecto. Si el proyecto tiene épicas o macros, el select del estado estará bloqueado en esta vista. El deadline se podrá indicar, pero vendrá vacío por defecto. Donde se especifique el repositorio se podrá crear uno nuevo (pulsar Enter en sus campos solo añadirá el repositorio, no guardará el proyecto), y también se mostrará el listado de los existentes para poder asociarlos al proyecto. El path del repositorio se podrá escribir a mano en un input de texto. Junto a él habrá un botón que abrirá un selector de carpetas, que escribirá el resultado en ese mismo input, y este seguirá siendo editable a mano. Si el input se edita, al perder el foco se comprobará que la carpeta existe. Si no existe, el marco del input se pondrá en rojo para indicar el error, pero no se bloqueará el guardado: se podrá guardar tal cual. Si el slug editado a mano ya existe, se le añadirá un contador como sufijo, igual que al generarlo: "_2", "_3", "_4", etc. El path pertenece al repositorio: es la ruta donde se ha hecho la copia local con git. Los repositorios son entidades propias e independientes de los proyectos, que solo se asocian a ellos mediante la tabla de cruce. Por eso, si se cambia la ruta, se cambia en la tabla repos y afecta a todos los proyectos que tengan asociado ese repositorio. El formulario permitirá también editar y actualizar los proyectos existentes. Al entrar en el setting "Projects", el formulario estará vacío y el botón de guardar pondrá "Crear". Debajo del formulario se mostrará una tabla como catálogo de proyectos. Si se pulsa en uno, el formulario se rellenará con sus valores actuales, el botón "Crear" quedará oculto y se mostrará el botón "Actualizar". Si se pulsa de nuevo en el menú "Projects", la vista se refresca, se pierden los cambios no guardados y vuelve a mostrarse el botón "Crear". La tabla del catálogo mostrará el nombre, el slug, el estado, el deadline y el número de repositorios de cada proyecto. Al editar un proyecto se podrán desasociar sus repositorios: solo se elimina la asociación en la tabla de cruce y el repositorio sigue existiendo.
